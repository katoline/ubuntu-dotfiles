# PR作成

現在の作業内容をコミットし、GitHubへPull Requestを作成する。

## 前提

- このSkillは `/pr` Command本文から呼び出されたとき、またはユーザー発言の先頭トークンが `@pr` のときに使う。Command本文を受け取ったこと自体が明示起動の証拠であり、ユーザー発言に `/pr` と書かれているか・UI上のCommand名が見えるかを追加確認しない。先頭の `@pr` はMarkdownのコード表記・引用符で囲まれていても同じトークンとして扱う。いずれの場合も再確認・拒否せず、PR作成または具体的な失敗理由の報告まで手順を実行する。本文中で `/pr` や `@pr` に言及しただけの場合や、通常の自然言語で「PRを出して」と依頼された場合は実行せず、`/pr` または `@pr` を案内する。
- OpenCodeではClaude Code / Grokのフックは動作しない。`opencode.json` のpermissionルールとOpenCode標準の確認を安全境界として使い、確認を迂回しない。
- `git commit`・`git push`・`gh pr create` はそれぞれ独立した単一コマンドで実行する。`&&`・`;`・`|`・改行で他のコマンドと連結しない。確認が表示されたらユーザーの判断を待つ。
- permission確認を拒否されたコマンドは再試行しない。その操作を行わず、止まった段階と結果を報告する。
- コミット・push・PR作成はメインセッションから直接行い、サブエージェントへ委譲しない。
- `--no-verify`・`--amend`・force push・削除オプション・デフォルトブランチへのpushは禁止。`gh pr merge` はこのSkillの範囲外であり実行しない。
- 作業ツリーや履歴を壊す操作は行わない。秘密情報を含む `.env`・鍵・トークン・認証ファイルは読まず、コミット対象にも含めない。

## 手順

### 0. 検証

プロジェクトの `AGENTS.md` などに検証コマンド（lint・型チェック・テスト・ビルド等）が明記されていれば実行する。失敗したらコミットせず、失敗内容を報告して終了する。検証を通すためにテストをskipしたり、期待値を変更したりしない。

検証手順が明記されていなければ「未検証」として先へ進み、報告に明記する。

### 1. 現状把握

以下を確認する。

- `git status` で未コミットの変更・未追跡ファイルを把握する。秘密ファイルが含まれていないか、ファイル名や差分の範囲で確認する。秘密ファイルの内容は開かない。
- `git diff` と `git diff --staged` で変更内容を把握する。
- `git log --oneline -10` でコミットメッセージの文体を把握する。
- 現在のブランチを `git branch --show-current` で確認する。デフォルトブランチは `git symbolic-ref --short refs/remotes/origin/HEAD` の `origin/` 以降から取得し、取得できない場合のみ `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` を使う。
- 未pushコミットを確認する。`git rev-parse --abbrev-ref @{upstream}` が失敗（upstream未設定）なら全コミットが未push。成功したら `git log @{upstream}..HEAD --oneline` を見る。
- 作業ブランチに既存のopenなPRがあるか `gh pr list --head <ブランチ> --state open --json number,url` で確認する。

未コミットの変更も未pushコミットもない場合は、PRを作るものがない旨を報告して終了する。

### 2. ブランチ準備

- デフォルトブランチ上にいる場合は、変更内容を表す新しいブランチ（例：`feat/xxx`、`fix/xxx`、`docs/xxx`、`chore/xxx`）を作成して移動する。
- 既に作業ブランチ上なら通常はそのまま使う。ただし確認なしでpushできるのは `origin` の `feat/`・`feature/`・`fix/`・`bugfix/`・`docs/`・`chore/`・`refactor/`・`test/`・`hotfix/`・`perf/`・`build/`・`ci/`・`style/`・`revert/` 配下のブランチだけ。それ以外の名前なら変更を保持したまま適切な接頭辞の作業ブランチを作成する。

### 3. コミット

未コミットの変更は、後から `git log`・`git show`・`git blame` で個々の目的へ辿れ、必要ならその変更だけを安全にロールバックできる粒度でコミットする。複数の関心ごとがある作業を、PRが1つだからという理由で1コミットにまとめてはならない。

分割の基準：

- コミット前に、変更を関心ごと・独立して戻せる単位へ分類し、コミット案を組み立てる。設定、機能、Skill/Command、テスト、ドキュメントなど、別々に追跡・ロールバックできる変更はそれぞれ別コミットにする。
- 同じ機能を成立させる実装とテスト、設定とその説明など、片方だけでは不完全になるファイルは同じコミットにまとめる。単なる同一PR内の変更であることは、まとめる理由にしない。
- 実質1つの関心しかない小さな差分は、無理に分割しない。
- 今回の作業と無関係な変更が混ざっている場合は、questionツールで含めてよいか確認する。回答を得るまでコミットしない。
- 関心ごとに `git add <対象ファイル...>` でstageし、各コミットの直前に `git diff --staged` でそのコミットに含める変更だけを再確認する。全変更を一括stageして一度だけコミットする方法は避ける。

コミットメッセージ：

- 既存履歴の文体に合わせる。このユーザーは日本語の簡潔な1行が基本。
- そのコミット単体で変更内容が分かる文言にする。「更新」「修正」だけは不可。
- ハーネスの指示で attribution（`Co-Authored-By:` トレーラー）が必要な場合は、1行要約・空行・トレーラーの形でHEREDOCを使う。

```sh
git commit -m "$(cat <<'EOF'
<1行要約>

Co-Authored-By: <ハーネスの指示どおり>
EOF
)"
```

### 4. Push と PR 作成

- `git push -u origin <ブランチ名>` を単独で実行する。`/pr` 中に確認なしで許可されるのは、共通 `pr-mode.sh` の自動承認条件を満たす上記の作業ブランチ接頭辞だけ。条件に一致しない場合や plugin を読み込めない場合は確認を迂回せず、ユーザーの判断を待つ。
- 手順1で既にopenなPRがある場合は新規作成せず、pushによって更新されたPRのURLを報告する。
- openなPRがなければ `gh pr create` を単独で実行する。permission確認が出た場合はユーザーの判断を待つ。
  - タイトル：変更内容の要約（日本語）。
  - 本文：変更概要・関心ごとごとの変更点・検証結果を記載する。後から本文から該当コミットへ辿れるようにする。
  - 本文はHEREDOCで渡す。ハーネスの指示で `🤖 Generated with …` などのフッターが必要な場合は末尾に置く。
  - `--base` はデフォルトブランチを指定する。`.github/pull_request_template.md` があれば、その構成に従う。

```sh
gh pr create --title "<日本語タイトル>" --base "<デフォルトブランチ>" --body "$(cat <<'EOF'
## 概要
<変更の概要>

## 変更点
- <関心ごとごとの変更>

## 検証
- <検証結果。未検証の場合はその旨>
EOF
)"
```

### 5. 報告

PRのURL・ブランチ名・コミット内容・検証結果（未検証ならその旨）を簡潔に報告する。

## 注意事項

- force push・`--no-verify`・`--amend`・デフォルトブランチへの直接push・リモートブランチの削除はしない。
- `gh pr merge` は実行しない。
- `gh` が未認証・リモート未設定などで失敗した場合は、勝手に回避策を取らず状況をユーザーに報告する。
