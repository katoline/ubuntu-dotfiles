# 言語

応答・説明・コード内コメントは日本語で書く（サブエージェントも同じ）。成果物（README・コミットメッセージ等）の言語はプロジェクトの既存ドキュメントに合わせる（無ければ日本語）。コマンド・設定キー・パス・モデルIDは原文のままにする。

# Git操作の制限

- `git commit`・`git push`・PR の作成と更新（`gh pr create` / `gh pr new` / `gh pr edit`、`gh api` の `/pulls` 書き込み）は、ユーザーが `/pr` を起動したターン中だけ行う。作業が済んでも変更はワーキングツリーに残して報告する。「コミットして」「PRを作って」と頼まれても自分では実行せず、`/pr` の実行を案内する
- force push・デフォルトブランチへの push・`gh pr merge` は `/pr` 中でも行わない
- 作業ツリー・履歴・リモートを壊す操作（reset --hard / clean / 変更の破棄 / branch -D / stash drop / rebase / amend / リモートブランチ削除）はユーザーの明示的な指示があるときだけ。成果物を未コミットで置く運用なので、変更の破棄は特に慎重に

# 作業用worktree

- タスク用の worktree が既にあれば再利用し、無ければメインセッションが専用の worktree を作る。他セッションの worktree とブランチは削除しない
- 完了後、成果物がコミット済みか引継ぎ先へ移して同一内容と保存を確認済みで、未保存の tracked・untracked・ignored 成果物が無いことを確認したら、メインセッションがメイン checkout から具体的な絶対パスを指定した `git worktree remove <絶対パス>`（`--force` なし）で追加確認なく削除する。子セッションや worktree 内から自分で cleanup しない。cleanup のために勝手にコミットしない
- 未保存の成果物が残る・移送先と衝突する・削除に失敗する場合は worktree を保持し、理由とパスを報告する。`--force` で再試行しない

# ファイル削除・プロセス停止

- 削除は作業ルート（`~/Dev/kaishi`・`~/Dev/seino914`・`~/Dev/hobby`・`~/orca/workspaces`。定義は dotfiles の `.claude/dev-roots`）と一時領域（`$TMPDIR`・`/tmp/claude-*`）の内側だけ。対象は変数やコマンド置換ではなく具体的なパスで書き、`cd` と組み合わせない
- 開発サーバー等の停止は `pkill` / `killall` ではなく `kill $(lsof -ti :<ポート>)` か PID 指定の `kill` で行う

# 変更後の検証

- 検証コマンド（lint・型チェック・テスト・ビルド等）はプロジェクトの `AGENTS.md` / `CLAUDE.md` にある前提。あれば変更後に必ず通す。無ければ探し回らず、報告に「未検証」と明記する
- 落ちたら自分で直す。自分の変更と無関係な既存の失敗は直さず報告する。テストの skip・削除・期待値の書き換え、lint / 型チェックのルール無効化・除外追加で「通す」のは禁止（必要なら理由を添えて提案に留める）
- `/pr` は検証が通っていることが前提

# レビューの範囲

レビューする側（レビュー用サブエージェント・セルフレビュー・`/code-review`）と、指摘を受けて直す側の両方に適用する。

- 前提は部品の脅威モデルで決める。**外部の入力・利用者に晒される部品**（API・Web画面・認証認可・外部データの処理・外部入力から組み立てるシェル / SQL / パス・秘密情報・権限境界）は攻撃者がいる前提で見る。**自分たちだけが操作する部品の事故防止**（CLI のフック・開発用スクリプト・ヒューリスティックな検査）は普通の使い方で起きる事故だけを見て、難読化や敵対的入力による回避は指摘しない。迷ったらプロジェクトの脅威モデル、無ければ「外部の入力が届くか」で決める
- 指摘ごとに再現経路を1文で書く（事故防止なら「普通の使い方でどう起きるか」、セキュリティなら「攻撃者が何を操作して何を得るか」）。書けないものは出さない
- 指摘しない：現実に来ない規模・形の入力での性能、好みの問題、ドキュメントに「対象外」「既知の制約」とあるもの
- 直す側は「直す / 対象外」に仕分け、対象外は理由を一言添えて報告する。同じ部品に同種の指摘が2回続いたらパッチを重ねず、セキュリティ境界なら許可リスト型の検証やフレームワーク任せへの設計変更を、事故防止なら対象外の明文化か設計の単純化をユーザーに提案する
- 修正後の再レビューは、修正した差分だけを対象にする

`.env`・秘密鍵・トークン類は読まない・出力しない・コミットしない。設定例は `.env.example` 等のテンプレートを使う。

# パッケージインストールの制限（Nix運用）

グローバル環境は `~/Dev/kaishi/ubuntu-dotfiles` の home-manager で宣言管理している。開発中に勝手に変えない。

- プロジェクト外に恒久的な影響が出るインストール（`apt` / `snap` / `npm install -g` / `pip install --user` / `nix profile install` / `nix-env -i` 等）と `home-manager switch` はユーザーの明示的な指示があるときだけ。グローバル（dotfiles の `nix/packages.nix` 等）への追加が要ると判断したら提案に留める
- `sudo` は実行できない。必要ならコマンドを示してユーザーに依頼する
- ツールはそのリポジトリの `flake.nix` devShell に宣言する（新規プロジェクトは `/nix-setup`）。エージェントのシェルでは direnv が効かないので `nix develop -c <cmd>` か `direnv exec . <cmd>` で実行する。一時的な確認は `nix shell nixpkgs#<pkg>` / `nix run` でよい
- lock ファイル管理のプロジェクトローカル依存（`npm install`・`pnpm add` 等）は通常どおり使ってよい

# サブエージェント

メインセッション向け（サブエージェントとして起動されたら本節は無視し、与えられた指示を実行する）。

- メインは要件整理・設計・分解・指示・レビュー・最終判断に専念し、実装と複数ファイルにまたがる調査は切り出す（1〜2ファイルの確認・自明な局所修正・設計と不可分な難所はメインがやってよい）
- 指示は自己完結させる（対象ファイル・設計方針・制約・完了条件）。独立したタスクは並列に起動する
- 委譲は範囲を絞る：分かっている事実（調査済みの結果・対象ファイル・前提）は渡して再調査させない。調べものは問いを具体的に列挙し、確認できないものは深追いせず「確認できず」と報告させる
- 成果物はメインがレビューしてから完了とする。報告は「変更ファイル／実行した検証と結果／未解決点」の形で受け取る
- 挙動に関わる変更（ドキュメントのみ・数行の自明な修正は除く）は、完了前に新しいコンテキストのレビュー用サブエージェントへ差分と要件だけを渡して独立レビューさせる。報告させるのは「レビューの範囲」に当てはまる欠陥だけで、採否はメインが判断する
- モデルの振り分けは各CLIの固有指示に従う

# 要約（compact）時に残すこと

変更したファイルの一覧と検証済み / 未検証、実行した検証コマンドと結果（失敗ならその内容）、サブエージェントの担当・状態と未解決点、ユーザーが確定した決定事項と判断待ちの事項。
